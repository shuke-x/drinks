## 4. 记录与图片治理契约

### 记录保留与分享

- 从数据库创建时间起保留 7 天，编辑、提交、审核和修改品饮日期不续期；已有记录从迁移时起获得 7 天。
- 到期立即拒绝读取和变更；启动时及每分钟分批清理，每轮最多 500 条，包含私有内容、内嵌照片与分享副本。
- 删除先清空内容，墓碑保留至原到期时间；相关最小审计元数据按 7 天清理。
- 备份排除 drink_records 表数据，恢复清除记录类审计副本；临时记录无法从灾备恢复。
- “另存为我的配方”创建正常私人酒单，不属于上述临时记录。
- 用户主动提交酒名、评价、实际配方、独立分享文字和勾选照片；私人笔记、价格、地点和参考配方原对象不自动公开。照片默认不选，分享照片重新编码清除元数据。
- 状态：private → pending → published/rejected；可撤回，编辑后恢复 private 并清空分享副本。审核需匹配版本且仅限 pending，不得审核自己的记录。
- records.review 默认仅赋给 super_admin，其他角色需授权；records.manage 不提供私人记录读取编辑入口。管理员只读取待审分享副本；不新增社区信息流。

接口均位于 `/api/v1`：

| 操作 | 路径与关键参数 |
| --- | --- |
| 提交分享 | POST /users/me/drink-records/:id/submit；version、caption、photoIndexes |
| 撤回 | POST /users/me/drink-records/:id/withdraw；version |
| 待审列表 | GET /admin/drink-records |
| 审核 | POST /admin/drink-records/:ownerId/:id/review；version、action、驳回必填 reason |
| 公开读取 | GET /public/drink-records/:ownerId/:id；仅通过且未过期的分享，不缓存 |

### /static 图片权限：代码与部署分别负责什么

已核对本地后端 `src/modules/upload/media.controller.ts`：`GET /static/:key` 先调用 `assertReadable`，再从所选存储读取，响应 `Cache-Control: private, no-store`。`src/main.ts` 将此路由排除在 api/v1 前缀之外；现有 `/assets` 指向 public，并非 uploads 直出。

- 已发布非私密酒单图片及当前头像可公开读取；其他图片通过服务端签发的短期凭据判断权限。
- 凭据有效 5 分钟、绑定图片与用户标识；读取时检查账号及归属/待审权限。持久化前去掉临时凭据，保存规范 URL。
- 上传挂载需校验归属；审核权限不能读取无关私人图片；存储桶保持私有。
- **生产操作**：部署新版 API，并检查 Nginx/其他代理的 `/static/` 配置。若使用 alias/root 直接读 uploads，应取消该直出，改为转发到后端 `/static/`，不能误加 `/api/v1` 前缀。
- 检查代理/CDN 是否覆盖 no-store、缓存私人响应；取消对应强制缓存并清理历史公开缓存。旧缓存不会因部署新代码自动消失。
- 本次未读取线上代理/CDN 配置，因此无法断言线上一定存在直出，也不能认定已修复。无需仅为此再次改写已完成的本地鉴权逻辑；发现线上版本或配置不一致后按实际差异处理。
- 验收：公开图片正常，私人图片无凭据/无权限不可读，过期或篡改凭据无效，审核者不能越权；不要把所有 /static 一律封禁而破坏公开图片。

6. 初期可保留 `STORAGE_DRIVER=local`。R2 准备好后按独立流程 dry run、暂停图片写入、复制并读回校验，全部成功才切换 s3；不删除源文件或恢复公开直出作为回滚手段。
7. 部署配套管理端并验收候选 App，配置实际备份调度、监控告警后完成商店发布准备。

### 工具与密钥条件

在服务端目录执行，具体变量契约见服务端 `.env.storage.example`：

```sh
pnpm media:migrate                       # dry run
pnpm media:migrate --apply               # 复制到私有 S3 并读回校验
pnpm backup                             # 暂停写入且 BACKUP_WRITES_PAUSED=true
pnpm backup:restore /secure/path/backup.tdbackup
```

备份使用 AES-256-GCM；BACKUP_KEY_BASE64 为独立 32 字节密钥，不能与备份同处保存或提交 Git。
恢复要求 RESTORE_CONFIRM=isolated、RESTORE_DB_NAME 以 restore_ 或 verify_ 开头、明确 RESTORE_DB_HOST/PORT/USER/PASS，以及尚不存在的 RESTORE_DIR。工具新建隔离数据库，不覆盖现有库，先校验密文与图片再恢复。
需要 pg_dump、pg_restore、createdb、psql 和 tar，或使用 PG_DOCKER_CONTAINER 提供数据库工具。临时记录不进入灾备；备份成功不等于已经证明可恢复。

## 8. 尚未实现的产品扩展（不是当前发现与记录定位的全部首发门槛）

家庭调酒助手目标：风味偏好 + 现有材料 + 可信替代 → 可执行配方。

| 阶段 | 规划能力 |
| --- | --- |
| V1 | 材料库存增删、标准名称/别名/分类、风味筛选、直接能做/缺一种分组与基础替代数据 |
| V2 | 临时材料输入、替代比例和风味变化、重新计算完整配方、结构校验、最多两种替代与最佳方案选择 |
| V3 | 明确口味反馈形成画像、临期材料优先、自然语言录入、采购建议和私人改编配方 |

结果分组：直接能做、替代后能做、只缺一种、缺少两种以上。装饰物不作为必需材料；经典原版、可靠替代和创意改编明确区分。关键身份材料设替代限制，无法可靠替代时如实说明。

配方需标准化风味维度、材料用量/单位/角色、必需性、替代许可、难度/时间/工具；替代规则需比例、兼容等级、风味变化、调整说明与限制。现有个人酒单“酒柜”不能等同于材料库存。

建议种子规模（规划，不代表已完成）：100–150 配方、80–120 材料、20–30 风味标签、30–50 替代关系、8–10 组核心材料限制。早期线上约 40 配方/5 风味方向仅为历史观察，本次未查询线上数量。

推荐可先用可解释规则，原规划风味/材料/难度/历史偏好权重 45/35/10/10 仅为待验证起点。替换两种标记创意改编，超过两种不再以原版展示。分步调酒、采购和材料匹配需要三端数据与运营闭环后才对外承诺；不依据一次差评排除整个风味，不引入饮酒量排行。
